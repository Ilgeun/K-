# SpecBridge 프로젝트 기록

2026 K-조선 해커톤(팀 조선컴국수) 출품작의 개발 기록이다. 무엇을 만들었고, 어떤 판단을 왜 했고,
무엇이 아직 검증되지 않았는지를 남긴다. 실행 방법과 구조는 [README](../README.md)를 본다.

- **한 줄**: 제조사 카탈로그(스캔 PDF 포함)를 AI가 정형 데이터로 바꾸고, 규칙이 선박 요구조건과 대조해
  대체 후보를 **충족 / 확인 필요 / 제외**로 판정하며, 판정 근거가 된 원문 페이지를 함께 보여준다.
- **설계 원칙**: AI는 읽고 구조화하고, 규칙은 판정하고, 담당자는 원문으로 확인한다.
- **현재 상태**: 계획서 제출 완료. 승인서 기반 프로토타입은 동작하고, 카탈로그 읽기 파이프라인은
  API로만 동작한다(화면 없음). 카탈로그 기반 판정·후보 구조는 미완성이다.
- **되돌리기 지점**: 승인서 버전을 git 태그 `approval-version` 으로 보존했다. 카탈로그 작업은
  `catalog-direction` 가지에만 쌓는다.

## 1. 왜 시작했나

해커톤 주제가 선박 기자재 대체품 검토였고, 처음 기획은 구매사양서·데이터시트·선급 규칙을 AI가 자동
대조한다는 아이디어였다. 그런데 선급 사이트(DNV 등)가 이미 승인된 기자재를 조회해 주므로,
**승인 여부가 아니라 내 조건에 맞는지 판단하는 일이 병목**이라는 가설로 차별점을 잡았다.
이 가설은 현업 인터뷰로 아직 검증하지 못했다.

## 2. 타임라인

| 단계 | 내용 |
|---|---|
| 1. 기획 검토 | 선급 검색 사이트와의 차이 정리, 요구조건·데이터 스키마 설계 |
| 2. 프로토타입 | FastAPI + SQLite + React. 요구조건 검색, 후보 비교, 검토 보고서 |
| 3. AI 추출 | 규칙 기반 → Claude(CLI/API) 이원화. 원문 인용 검증, 규칙과 교차검증 |
| 4. 실문서 평가 | 공개 선급 승인서 5건으로 추출 정확도 측정(정답은 추출 전에 작성) |
| 5. 기능 확장 | 선박 등록·선택·삭제, 다중 선급, 사용 제한 문장 해석 |
| 6. 문서·배포 준비 | 사용 가이드 이미지 12장, Railway용 Dockerfile·접속 암호·볼륨 |
| 7. 방향 전환 | 승인서 → 제조사 카탈로그. 태그와 별도 가지로 되돌릴 수 있게 분리 |
| 8. 스캔 카탈로그 읽기 | 이미지 읽기 파이프라인, 다회 읽기 다수결·표 구조 검사 |
| 9. 벤치마크 | 글자 레이어를 정답으로 삼아 이미지 읽기를 자동 채점 |
| 10. 제출 | 참가 신청서, 서약서, 계획서 PDF, 구글폼 답변 |

## 3. 핵심 설계 결정

- **AI와 판정의 분리** — AI는 문서를 값으로 바꾸기만 하고, 충족·제외 판정은 결정적인 규칙이 한다
  (`backend/app/engine.py`). 결과가 예측 가능하고 근거를 설명할 수 있다.
- **담당자 확정 전에는 판정에 반영하지 않음** — AI가 뽑은 값은 담당자가 원문과 대조해 확정한 것만 쓴다.
  믿기 어려운 항목만 골라서 확정하지 않을 수 있다.
- **자료가 없으면 통과가 아니라 "확인 필요"** — 모르는 것을 통과시키지 않는다.
- **원문 근거 표시** — 값마다 문서·페이지·인용문을 저장해 클릭하면 원문이 열린다.
- **값을 지어내지 않기** — 등급(PN, JIS K, Class)에서 설계압력을 만들지 않는다.
- **정직한 평가** — 정답표는 추출 전에 작성하고, 표본 크기와 신뢰구간을 적고, 결과를 본 뒤 추가한
  지표는 그렇다고 명시한다.
- **되돌릴 수 있는 방향 전환** — 큰 전환은 태그와 별도 가지로 분리하고 실패 기준을 미리 정한다.

## 4. 겪은 문제와 해결

| 문제 | 원인 / 해결 |
|---|---|
| Claude가 PN 등급(PN25)을 설계압력 25 bar로 해석 | 등급에서 압력을 만들지 말라는 프롬프트 규칙 추가 + AI 단독·불일치 항목은 기본 선택 해제 경고 |
| 구경 범위를 `"50-600"` 문자열로 주면 엔진이 범위로 못 읽어 DN200을 잘못 제외 | 추출 결과를 범위로 정규화하는 단계 추가 + 테스트로 고정 |
| 규칙 기반이 사용 제한의 조건을 무시하고 전면 금지로 읽음 | 목록·번호 항목의 문장 경계와 조건 처리 수정. **가장 위험한 오류는 놓침이 아니라 조건 무시한 전면 금지**였다 |
| 테스트가 실제 업로드 파일을 지움 | 테스트가 업로드 폴더와 DB를 임시 위치로 분리하도록 수정 |
| Claude CLI가 결과 JSON 뒤에 로그를 섞어 내보내 파싱이 간헐 실패 | 첫 JSON 객체만 읽도록 수정. **기존 텍스트 추출 경로도 같은 결함**이 있었고 실패 시 규칙 기반으로 조용히 대체되고 있었다 |
| 같은 표를 3번 읽었는데 2번이 같은 실수(열 누락)를 해서 맞은 1번이 제외됨 | 다수 형태만 기준으로 삼던 합치기 규칙의 약점. 제외된 읽기와 같은 종류 표의 열 수 불일치를 경고로 노출 |
| 원본이 빈칸인 셀을 "과반 없음"으로 잘못 세어 가짜 경고와 불필요한 재읽기 발생 | 과반이 빈칸인 경우와 과반이 없는 경우를 구분(`CellFlag.resolved`) |
| PDF를 이미지로 만들면 배경이 검게 나와 글자가 안 보임 | 투명 배경을 흰색에 합성한 뒤 전달 |
| **머리글보다 값 열이 많은 표에서 마지막 값을 놓침** | **미해결.** 두 번 읽어도 똑같이 틀려 경고가 뜨지 않는다. 열 자료형 검사로 잡을 계획 |

## 5. 정량 지표 (요약)

방법과 한계는 [backend/eval/REPORT_catalog.md](../backend/eval/REPORT_catalog.md),
승인서 시절 평가는 [backend/eval/REPORT.md](../backend/eval/REPORT.md)에 있다.

| 지표 | 결과 | 표본과 주의 |
|---|---|---|
| 카탈로그 표의 행 찾기 | 100% (174/174행) | Atlas 카탈로그 6쪽, 글자 레이어를 정답으로 사용 |
| AI가 읽은 값 중 틀린 값 | **0건** | 정답 값 1,941개 중 읽은 1,862개가 모두 정확 |
| 정답 값 중 읽어낸 비율 | 95.9% (화질 저하 95.2%) | 놓친 79개는 모두 "표의 마지막 값 누락" 한 유형 |
| 실제 스캔본 표 셀 정확도 | 527/527 | PK 카탈로그 치수표 **1쪽만** 측정 |
| 승인서 사양 추출 재현율(방향 전환 전) | 95% (35/37, 82–99%) | 승인서 5건, 정답은 Claude 작성·사람 검수 전 |
| 처리 시간 | 카탈로그 6쪽 약 80초 | 3쪽씩 동시 처리, Claude CLI 기준 |

모든 수치는 **소규모 자체 평가**다. 검토 시간 단축률은 아직 실측하지 못했다.

## 7. 확인이 필요한 것

- 제출한 계획서 PDF 6쪽 정량 지표에 **572/572셀 오타**가 있다(측정값은 527/527).
- 계획서는 **Gemini Flash**, 실제 구현·측정은 **Claude**다. 본선에서 쓸 AI 도구를 하나로 확정해야 한다
  (주최 측이 생성형 AI 툴 계정을 발급한다고 안내됨).
- 서약서의 제3자 데이터 이용약관 준수, 생성형 AI에 타인 저작물 입력 금지 조항과 관련해
  **카탈로그 사용 조건 확인**이 필요하다.
- **로고 이미지의 출처와 사용 조건** 확인이 필요하다.
- 본선 일정 미확인.

## 8. 배운 것

- **AI 결과를 검증하는 설계**: 원문 인용 검증, 규칙과의 교차검증, 여러 번 읽어 비교하기. 그리고
  이런 검증이 못 잡는 오류(모든 읽기가 같은 실수를 하는 **체계적 오류**)가 있다는 것을 직접 측정해 확인했다.
- **정직한 평가**: 표본 크기, 정답의 출처, 결과를 본 뒤 정한 규칙을 함께 밝히지 않으면 수치가 과장된다.
- **독립적인 정답을 만드는 방법**: 글자 레이어가 있는 PDF는 AI 없이 정답을 뽑을 수 있어, 스캔 읽기
  성능을 재현 가능하게 자동 측정할 수 있다.
- **데이터 소스가 서비스의 범위를 정한다**: 승인서에서 카탈로그로 바꾸면 판정할 수 있는 요구조건이
  7개 중 3개로 줄어든다.
