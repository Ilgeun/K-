# 제조사 카탈로그(스캔 이미지) 읽기 시험 (소규모, 2쪽)

- 작성일: 2026-09-21 · 대상: PK Valve & Engineering 버터플라이 밸브 카탈로그 18쪽 중 **3쪽(규격 목록)·9쪽(치수표)**. 쪽마다 이미지 1장인 스캔 PDF(글자 레이어 없음).
- 방식: `claude -p --tools Read --allowedTools Read` 로 이미지 파일을 읽게 하고 `--json-schema` 로 구조화 출력. **앱 코드에는 아직 연결하지 않았다**(시험용 호출).
- 정답: **추출 결과를 보기 전에** 이미지를 보고 사람이 옮겨 적었다(표 527셀, 목록 사실 26건). 작성자는 Claude 이고 사람 검수 전이다. 정답표·원본 결과는 저작권 자료라 저장소에 넣지 않았다(`backend/data/eval/labels_catalog_*`, `backend/eval/cache_catalog/`는 gitignore).
- 문서 내용이 Anthropic 으로 전송됐다. 이 시험의 CLI 호출은 총 5회(표 읽기 3, 목록 읽기 1, 누락 확인 1)이다.

## 결과

| 시험 | 대상 | 결과 |
|---|---|---|
| 표 읽기 | 9쪽, Class 150·300·600 치수표 | 1회차 **526/527 셀(99.8%)**, 2·3회차 **527/527**. 행 누락 0 |
| 목록 읽기 | 3쪽, STANDARD/OPTION 두 열의 규격 목록 | 사실 26건 중 **24건 일치**, 오답 0, **누락 2**(상단 문장 "ASME B16.34로 설계", "Fire safe design"), 지어낸 항목 0 |

## 오류의 성격

- **표: 조용한 오답.** 이웃 행의 값을 가져옴(Class 300 6"의 `h1` 22.2 → 25.4). 구조 규칙(단조성·크기 짝·열 간 종속)으로는 걸러지지 않고, **같은 이미지를 독립적으로 여러 번 읽어 비교**해야 잡혔다.
- **목록: 문장 누락.** 페이지 상단의 한 줄 문장(설계 규격, 내화 설계)을 건너뜀. 값이 틀리는 것이 아니라 **없어서** 판정에서 빠질 수 있다. 원문 대조가 아니라 "표에 없는 문장이 있는가"를 묻는 2차 패스로 잡았다.

## 검증 장치(앱 코드: `app/catalog_checks.py`, 테스트 14개)

| 장치 | 잡는 것 | 못 잡는 것 |
|---|---|---|
| `check_table` 구조 검사 | 크기 짝(3"=80mm 등)·순서·중복·열 단조성(원본 이상값은 severity=review) | **그럴듯하게 틀린 값** |
| `check_dependency` | 같은 장착 TYPE인데 치수가 다른 경우 | 위와 같음 |
| `compare_reads` | 읽기끼리 어긋난 셀, 과반 값 제안, 과반 없으면 추가 읽기 필요 | **모든 읽기가 같은 오답인 체계적 오류** |
| 누락 확인 패스(LLM, 앱 미연결) | 추출 목록에 없는 문장 | 페이지 밖 내용, 잘못 읽은 값 |

## 한계 (반드시 함께 말할 것)

1. **표본이 매우 작다.** 2쪽, 오답 1건. 검증 장치가 "오답 1건을 잡았다"는 것이 일반적인 검출률을 뜻하지 않는다.
2. **누락 확인 패스의 지시문은 '3쪽에서 상단 문장이 빠진다'는 것을 안 뒤에 만들었고 같은 쪽에서 시험했다**(지시문 자체는 일반적인 표현이지만 낙관적 수치).
3. 읽기 횟수만큼 시간·사용량이 늘어난다(9쪽 1회 약 50초, 3쪽 약 20초, 누락 확인 약 11초). 호출 비용은 CLI가 보고한 환산값(1회 약 $0.08)만 확인했고 구독 사용량으로 어떻게 잡히는지는 모른다.
4. **서버 배포에서는 Claude CLI를 쓸 수 없다.** 같은 방식을 API 키의 이미지 입력으로 옮겨야 하며 이는 시험하지 못했다.
5. 정답은 Claude 가 이미지를 읽어 옮겼다(틀린 1건은 이미지를 확대해 직접 확인). 같은 계열 모델의 공통 착각이 있을 수 있다.
6. 이 카탈로그는 금속 시트 트리플 오프셋 산업용 밸브다. 선박용 고무 시트 밸브 카탈로그에서도 같은 결과가 나온다는 보장은 없다.

7. **API(이미지 입력) 경로는 스텁 테스트만 했고 실제 호출은 검증하지 못했다.** 서버(Railway) 배포에서는 CLI를 쓸 수 없어 이 경로가 필요하다.
8. 화면(UI)은 아직 없다. 이 결과는 API로만 얻을 수 있고 후보·판정에는 연결되지 않았다(4-2·4-3).

# 카탈로그 읽기 벤치마크 — 글자 레이어를 정답으로 (Atlas Marine Valves, 2026-09-21)

`python -m eval.catalog_bench run|score PDF 쪽,... clean|scan` (코드: `eval/catalog_bench.py`, 테스트 7개)

## 방법
- 대상: Atlas Marine Valves 카탈로그(48쪽, 글자 레이어가 있는 PDF) 중 **표가 한 줄에 한 행으로 뽑히는 6쪽(30~34, 36쪽), 정답 174행·토큰 1,941개**.
- **정답: PDF 글자 레이어에서 정규식으로 뽑은 행.** AI·사람이 정답을 만들지 않는다. 쪽 이미지는 맥의 `sips`로 렌더링(투명 배경은 흰색에 합성).
- 시험: 그 쪽을 **이미지로만** 보여 주고 파이프라인(`catalog_read.read_page`, Claude CLI)이 표를 읽게 한 뒤 행 단위로 비교. 행은 MV 코드로 짝짓고, 토큰은 대문자·`4x M16` 표기를 통일해 비교한다.
- 조건: **clean**(디지털 렌더링 그대로) / **scan**(해상도 50%, JPEG 화질 45, 0.6° 기울임으로 스캔본을 흉내 냄 — 실제 스캔이 아님).

## 결과 (조건별 1회 실행)

| 지표 | clean | scan(흉내) |
|---|---|---|
| **행 재현율** (코드로 행을 찾음) | **174/174 = 100%** (95% 97.8~100%) | **174/174 = 100%** |
| **값 정밀도** (AI가 적은 값이 정답과 일치) | **100%** (틀린 값·지어낸 값 0) | **100%** |
| **값 재현율** (정답 토큰을 찾음) | **95.9%** | **95.2%** |
| 행 완전일치율 (행의 모든 값이 정답과 같음) | 95/174 = **54.6%** (47.2~61.8%) | 81/174 = **46.6%** (39.3~54.0%) |
| 경고로 잡힌 오류 행 | **0 / 79** | **0 / 93** |
| 처리 시간 | 6쪽 약 80초(병렬 3) | 약 89초 |

- **틀린 행은 전부 한 가지 유형**이다: 행의 **마지막 값 누락**(clean 79행, scan 93행). 값 오독(숫자를 잘못 읽음)은 **0건**, 지어낸 값도 0건.
- 원인(이미지로 확인): 31~33쪽(scan에서는 36쪽도) 표에서 `Holes x dia` 머리글 하나 아래에 **값 열이 둘**(구멍 수 `4`, 볼트 `M12`)이고 그 뒤에 `L`(40)이 있다. AI가 머리글 개수(9개)에 값을 맞추면서 `M12`를 `L` 열에 넣고 **진짜 `L` 값을 잃었다.** 같은 이미지를 두 번 읽어도 **똑같이 틀려서 읽기 일치 검사(다수결)로는 경고가 뜨지 않았다**(체계적 오류).
- **정답 파서가 못 읽은 표가 있다**: 36쪽의 두 표(Lug형, 11행)는 글자 레이어에서 한 줄 한 행으로 뽑히지 않아 정답에 없다. AI 는 이 행들을 (이미지로 확인하면 실제로 있는) 값으로 읽었다. 이 11행은 채점에서 제외했다.

## 채점 규칙 중 결과를 본 뒤 정한 것 (반드시 함께 말할 것)
- 표의 **세로 구분선을 옮겨 적은 `|` 기호는 무시**한다(값이 아니다). 이 규칙 없이는 clean 행 완전일치율이 46.6%(36쪽 14행이 불일치로 채점됨)다. 규칙은 36쪽의 불일치를 이미지로 확인한 뒤 정했다.
- 오류 유형 분류(`마지막 값 누락` 등)와 정밀도에서 '정답에 없는 코드의 행' 제외도 결과를 본 뒤 추가했다.

## 한계
1. **카탈로그 1권, 6쪽, 표 배치 3~4종**이다. 행은 같은 배치가 반복돼 서로 독립이 아니므로 **행 단위 신뢰구간은 실제보다 좁다.** 배치 단위로 보면 "잘 읽은 배치 3, 못 읽은 배치 3"에 가깝다.
2. **가장 어려운 쪽이 빠졌다**: 글자 레이어에서 열 단위로 흩어지는 28·29쪽은 정답을 자동으로 못 만들어 제외했다(선택 편향).
3. 조건마다 **1회 실행**이다(비결정적). 같은 쪽이 다른 실행에서 다르게 읽힐 수 있다(PK 카탈로그 11쪽에서 실제로 관찰).
4. 'scan' 조건은 **시뮬레이션**이다. 실제 스캔의 얼룩·그림자·구겨짐은 반영하지 않았고, PK 카탈로그(실제 스캔)로 잰 것은 9쪽 표 527/527, 다른 쪽은 정답이 없다.
5. 정답은 글자 레이어 파서라서 **글자 레이어가 틀린 PDF에서는 틀린다**(불일치 행 3쪽을 이미지로 대조해 일치 확인, 전수 확인은 아님).
6. Claude CLI(`claude-sonnet-5`)로만 시험했고 **API 이미지 입력 경로는 미검증**이다.
7. 이 결과로 알게 된 결함(머리글보다 값 열이 많은 표에서 마지막 값 누락, 다수결이 못 잡음)은 **아직 고치지 않았다.**
